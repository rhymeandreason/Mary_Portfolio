hack-computer.com

A "hackable" OS for teaching kids about code and computational thinking, with a cast of characters and games that are solved by hacking the game's code.

A spin-off of Endless, the Linux OS for emerging markets, HACK shipped as an all-in-one Asus laptop with new content every month.

Learning from Kids & Parents

At the time I joined, the team was deep in production mode to make their monthly game releases. My task was to untangle some of the more platform-level UX challenges.

We had weekly playtest and user research sessions with kids. While the kids enjoyed the games, they would benefit from a more explicit learning progression. Since our age range of 8–12 spans many grades, we needed to let kids have agency over their own speed and difficulty level.

More than half of our playtesters were familiar with Scratch. In 2019, the problem isn't introducing coding, it's going deeper.

Comparable Products

I referenced Processing.org and Khan Academy, which have a proven track record of teaching coding in an approachable manner. Significantly, the Processing language is designed with teaching in mind, and is a logical next step to follow Scratch.

Learning Progression

I proposed that the team take a lesson-focused approach in contrast to level-oriented gameplay. I borrowed many ideas from Khan Academy, but infused more of our existing visual and storytelling language.

Lessons explain a specific coding concept. For instance, how to use color() and fill().

Exercises are quick puzzle-like challenges to reinforce the lesson. They require only a few lines of code to complete. I took inspiration from physical activity books in how these are designed.

Projects are unlocked after a series of related lessons. A project has multiple steps and can guide kids to combine parts of previous code sketches.

Challenges are extra credit. They can incorporate lessons from other school subjects, like art theory or science. The instructions are less explicit than a Project, so the kid has to figure out more steps herself.

Non-Linear Progression

The current Hack games were built with linear quests and levels, so if a kid was stuck on a level, they couldn't do anything else.

I made a map of how coding lessons could be unlocked to enable exploration in multiple directions, much like how a map is uncovered in a game. This was also useful in planning out how much content we were building.

A Coding Sketchbook

Instead of building a whole new game every month, I proposed we build one app for creating lesson and story content in a modular way, and in the future enable kids to publish their work.

This Code Sketchbook concept draws upon how Processing works in "sketches," and how scientists work in Jupyter notebooks.

To quickly validate the concept, I ran a super low-fi playtest using the online P5.js editor and walking through a Processing lesson. Our 13-year-old playtester was enthusiastic about the "freedom" of coding in Processing, and said he preferred it to the game he also tried.

Storytelling with Code

The team had many ideas for stories and side quests that didn't fit within the linear episodes. Why not use the code itself to express these ideas?

The Hack characters would have their own sketchbooks inside the app, with work that fit their interests and personality. Our engineers and writers loved this idea, and it would be a fun, easy way for the whole team to contribute to the storytelling.

Toolbox UI Improvements

Before making any new apps, we needed to improve the existing product. The Toolbox is the "hacking" interface that kids write code in. Since visual design was already far along, I made wireframes focused on interaction.

  • Made the UI more modular, so sections could be locked and unlocked more easily, and development would be simpler.
  • Cleaned up variable names in the code to be more learning-friendly, and matched them in the UI.
  • Made the Reset button more prominent, a problem found in playtesting.
  • Made the current Level more prominent.

Coding Helpers

The Toolbox needed to be more like a kid-friendly IDE. Because we don't use blocks, we needed features that guide learners through the common issues of typing code.
